### A. Look- and kit-supplied sprite art with mipmaps (closes the custom-art row): M, opus-high

- What, in `evani-render` behind a new feature `sprite-art` (turned on by a kit or look that supplies art, like `pixel-art` today; games that only use built-in shapes don't download it):
  - Several named sheets packed into the one atlas texture: a `SpriteArt` resource holding sheets from the engine, the look and the kit; frames get names; a deterministic shelf packer places them with a gutter of `2^(mips-1)` px around each frame; `SpriteArt::cell("piece.heart") -> Option<u16>` with a fallback to a built-in shape, so a kit never depends on a specific look. The existing `SpriteSheet` stays as the kit's sheet, so the platformer keeps working unchanged.
  - Mipmaps: the atlas gets a full mip chain built on the CPU at upload (sRGB-correct box filter, per frame, so gutters stop bleed); the linear sampler uses `MipmapFilterMode::Linear`. Pixel-art sheets (`render.pixel_art`) keep level 0 and the nearest sampler.
  - Looks supply art through the existing generator path (`GeneratedAsset` gets a `SpriteSheet` variant, crates/evani-core/src/plugin.rs:353), so art comes from the look crate, never the kit.
  - Atlas size is clamped to the device's `max_texture_dimension_2d`; a sheet that doesn't fit is an `ErrorLog` entry, not a crash.
- Plugs into: match-3 (the `cartoon2d` look supplies heart, wrapped-sweet and other piece shapes; the kit asks by name, built-in shapes as fallback). The 2d-platformer may move its frames to names (no visual change; geocheck-2d must stay clean). Kit changes go through `fix match-3` / `fix 2d-platformer` and keep status `review`.

### C. Shared GPU particle system (closes the particles row): L, opus-high

- What:
  - `evani-core`: a tiny always-present `ParticleQueue` resource with `emit(Emit { pos: [f32; 3], vel: [f32; 3], color: [f32; 4], life: f32, size: f32, shape: u16, space: Screen2d { layer } | World3d, gravity: f32, drag: f32 })` and `burst(..)`. With no particle system in the build it is drained each step, so kits call it without a feature (the same pattern as the `AudioMixer` no-op voices).
  - `evani-render`: a `compute` pass kind in `RenderGraph` (feature `compute`, turned on only by effects that need it).
  - `evani-fx` `particles` (the existing feature, now also turning on `evani-render/compute`): a pooled storage buffer sized to the tier cap; new particles uploaded from the queue each step; a compute pass that integrates every live particle per fixed 60 Hz step (gravity, drag, life); one instanced draw per space (2D layer sprites; 3D camera-facing quads, depth-tested, alpha or additive by shape) using atlas cells or A's named frames. The oldest is recycled at the cap.
  - Tier caps: add a numeric `max_particles` to assets/tiers/*.json as plain numbers converted from catalog/tiers.json's strings ("2,000" becomes 2000; so 2000 / 10000 / 50000 / 250000, VR 5000), read into `TierPreset`, and `cap_follows_the_tier` checks them against the catalog; `fx.particles.max` stays as the game's own lower cap.
  - Determinism: emits come from the fixed step on the kit's own seeded `Pcg32` stream (effects on or off never change the game); the compute pass steps by sim ticks, not wall time, so stepped-clock captures repeat exactly. Natively (tests, the native bench) a CPU reference of the same integration counts what the GPU would draw.
