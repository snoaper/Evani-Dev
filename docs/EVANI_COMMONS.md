# Evani.commons: sharing better asset versions

Evani.commons is Asset Studio as it ships inside Evani.App: anyone improves a procedural library asset in rounds (an author helper and its own independent reviewer, scored against a stored reference), then **shares** the better version to Evani.app, where other Evani users browse, download and adopt it. The **server decides** what is published: it rebuilds every upload from its code, renders it with its own cameras and hidden angles, scores it with its own reviewer and takes it only when that score beats the published version for the same asset and art style.

This file is the Evani.Dev side: the package, the commands, the tab. The website, the server check and the bridge the tab calls are Evani.App's (its `docs/evani-commons.md`, the shared contract). The release plan is `.vibedeck/plans/evani-commons-release.md`.

| Part | Where |
|---|---|
| Package format `evani-commons/1`, exporter, verifier, importer, share hint | `tools/xtask/src/commons.rs` (`cargo xtask commons ...`), tests in `commons_tests.rs` |
| The tab: rounds, Share, Browse, Adopt, settings | `tools/evani-commons-tab/` (the bundle: Evani.App ships it as the built-in tab `evani-commons`; this project's custom tab `asset-studio` runs the same code) |
| The tab's Evani.commons tests (a mock of the bridge) | `tools/studio/commons-tab-test/commons.mjs` |
| The server's render app: the asset alone in the realism studio, with its own cameras (orbit, player, two-view), sun, mask, stats, test scenes and measures | `examples/proc-field/apps/commons-render`, the kit's `commons` feature (`src/commons.rs`, `src/scenes.rs`), `tools/studio/asset-shoot.mjs --stats --measure` |
| Upload, list, download, the server check, the Share card | Evani.App (not this repo) |

## 1. An asset version

One asset (its library key, the `basic!` key in `crates/evani-procedural-lib`) in one art style (`photoreal`, ...), as a column round left it: its code change against the engine commit it was built on, the live params of its scored picture, its independent score, the reference and the round pictures. No meshes, textures or wasm: code and params only, so a version is small and anyone can rebuild it (engine lightness).

## 2. The package (`evani-commons/1`)

A folder `<asset>@<style>-<hash12>/`:

```
commons.json            the manifest
patch.diff              unified git diff (-U3, LF, --full-index) against engine.commit, allowed paths only
code/base/<path>        each touched file as it is at engine.commit, for a 3-way merge when the adopter's copy differs
params.json             {"kit.<id>.<name>": number}: live param overrides of the scored capture ({} when none)
reference.jpg           the reference as the maker saw it (<= 1600 px; shown, never trusted)
reference-original.png  the image generator's untouched file (C2PA credentials kept): a new Community item's provenance
rounds/round<N>.jpg     view 0 of round N (<= 1024 px); rounds/round<N>-v<V>.jpg the other views (at most 6 pictures)
LICENSE                 MIT, "Copyright (c) <year> <author>"
README.md               what it is, its score, how to adopt it
```

`commons.json` (written by the exporter; every field is there, `null` when unknown):

- `format` `"evani-commons/1"`; `asset` {`key`, `category`, `name`, `style`, `feature` = `evani-procedural-lib/<key>`}; `area` `official` (the asset is in the base's catalogue) or `community`; `based_on` the hash12 of the published version it improves.
- `version` {`column`, `round`, `branch`, `commit`, `made` = the round commit's own date}; `score` {`value` 0-5 in half stars, `scale`, `independent: true`, `reviewer_model`, `reviewer_account`, `reviewed_at`, `author_model`, `summary`}.
- `score.categories` (Asset Studio v1.5.36; **present only for a round scored in categories**, absent from a classic round's package): {`scale` `"0-20 per category; total out of 100"`, `weights` {`silhouette` 25, `structure` 25, `material` 20, `colour` 15, `lighting` 15}, `scores` {each category: a whole number 0-20}, `reasons` {category: the reviewer's reason, up to 240 characters; empty ones left out}, `total` 0-100}. The exporter takes it with `--categories <file.json>` (`{scores, reasons, total}`, as the tab stores the round), works the total out again from the scores and refuses the export when the total's half-star value (total / 20 to the nearest half) differs from `--score`. `score.value` stays the half-star number. This is the radar chart's data: `tools/evani-commons-tab/radar.js` (one standalone file, no dependencies) draws it the same way on the website as in the tab.
- `reference` {`file`, `sha256`, `source_sha256` (the stored picture it was made from), `generator`, `prompt`, `made`, `original`, `original_sha256`}.
- `engine` {`version` (the workspace version at the base), `commit` (the base, 40 hex), `base_blobs` {path: git blob sha}}.
- `code` {`patch`, `paths`, `sha256`, `bytes`, `base_dir`, `files` [{`path`, `status` added|modified|deleted, `base_sha256`, `after_sha256`}]}; `params` {`file`}.
- `render` {`app` `examples/proc-field/apps/proc-field`, `scene_feature` (the round's dev scene, or null), `asset_feature`, `view_param`, `views`, `size`}: how the maker shot it. The server builds the generic field (no scene feature, only the asset's library feature) for its own cameras.
- `licence` {`spdx` `MIT`, `author`, `year`}; `pictures` [{`file`, `round`, `view`, `sha256`, `width`, `height`}]; `content_hash`.

**Content hash.** `"sha256:"` + SHA-256 of the sorted lines `<sha256 hex>  <relative path>\n` (two spaces, `/` separators, byte order) for every file except `commons.json`, then one last line `<sha256 of commons.json as written with "content_hash": "">  commons.json\n`. The exporter writes the manifest with that placeholder, hashes it, then fills the value in place; a reader puts the placeholder back (the one `"content_hash": "sha256:<64 hex>"`, exactly one space after the colon) before hashing. Any change to code, params, pictures or manifest changes it.

**What may travel** (the exporter, the importer and the server all enforce it):

- Paths: `crates/evani-procedural-lib/**`, `crates/evani-procedural/**`, `crates/evani-material-recipes/**`, `crates/evani-material-nature/**`, `crates/evani-material-proc/**`, `crates/evani-material-layers/**`, `crates/evani-grass/**`, `examples/proc-field/**` (the dev scene; the server drops it from its build), `catalog/procedural/library.json`. Text files only (`.rs`, `.wgsl`, `.toml`, `.json`, `.md`), plain ASCII paths, no `..`, no links, no renames, no binaries. Never a `Cargo.lock` or a `build.rs`. `catalog/procedural/references.json` is project data: the importer writes the adopted score into it itself.
- A changed lock file or crate manifest outside those paths (new dependencies) refuses the export; docs and `DECISIONS.md` lines are just left out (the export lists them).
- Code safety: shared code is built on the adopter's PC and on the server. A `Cargo.toml` may change only its `[features]` table (no new dependencies, no build or proc-macro crates, no new or removed crates). Added Rust lines may not use `std::process`, `Command::new`, `std::net`, `TcpStream`/`UdpSocket`, `std::fs`, `std::env`, `std::os`, `std::ffi`, `unsafe`, `extern "`, `#[link`, `#[no_mangle]`, `include!`, `asm!`, `libc::`/`winapi::`/`windows_sys::`, an `include_str!`/`include_bytes!` path with `..`, or a `use std::{...}` group naming fs, process, net, env, os or ffi. Pure comment lines are not read. A refusal names the file, line and rule.
- Sizes (the bridge's limits): at most 64 files, each at most 2 MB (`reference-original.png` 8 MB), 12 MB in total. Real packages: the clouds' round 5 (4 files of code) is 115 KB of code and 44 KB of pictures, plus the 1.76 MB untouched reference original.
- Licence: MIT only, with its LICENSE file.

## 3. The commands

```text
cargo xtask commons export --asset <key> [--style photoreal] [--commit <ref>|--branch <ref>] [--onto <ref>] [--base <ref>]
        --score <0-5> --independent --reviewer-model <m> [--reviewer-account <a>] [--reviewed-at <iso>] [--author-model <m>] [--summary <s>]
        [--column N] [--round N] [--reference <png|jpg>] [--reference-original <png>] [--reference-generator <g>] [--reference-prompt <p>]
        [--picture [r<R>v<V>=]<png|jpg>]... [--params <json>] [--scene <feature> --view-param <p> --views 0,1 --size WxH]
        [--area official|community] [--based-on <hash12>] [--author <name>] [--out <folder>] [--dry-run]
cargo xtask commons verify <folder>
cargo xtask commons import <folder> [--root <project>] [--dry-run] [--server-score <x>] [--version-id <hash12>] [--check|--no-check]
cargo xtask commons gate --score <x> [--independent] [--published <y>|none] [--floor 3.0]
cargo xtask commons locked-ref --asset <key> [--style photoreal] --sha256 <hex> [--site <api>]
```

- **locked-ref** (v1.5.48) puts Evani.app's locked reference for an item into the project at `.evani/commons/locked/<asset>/<style>/locked-<sha12>.<jpg|png|webp>` (under `.evani`: never committed, never in a download): already there, else the catalogue file `apps/material-view/assets/proc-refs/<asset>.jpg` or any version of it in the git history, else read-only from the public API (`--site`, default the live API: `GET <site>/public/commons/<asset>/<style>/reference`). It writes the file only when its SHA-256 is exactly `--sha256`, and never uploads, replaces or changes anything on the website. Asset Studio scores a locked item's column against it (docs/ASSET_STUDIO_GUIDE.md 2.5). Tested: `locked_ref_puts_the_locked_picture_in_the_project` (history, already there, a `file://` copy of the API, a wrong picture refused with nothing written, no answer, bad keys).

- **export** packs one round. The base is `--base`, else the merge base of the round's commit with `--onto` (default: the branch the project's main checkout is on). It refuses a version without an independent review (`--independent` and a reviewer model; never the author's own), rebuilds every file from the diff and its base copy and compares it with the round's commit (so a package always applies to its own base), re-encodes PNG pictures as JPEG (quality 85, box-filtered down), checks the original reference for C2PA credentials, and verifies the finished folder. Output: `<out>/<asset>@<style>-<hash12>/` (default `<project>/.evani/commons/out`; the tab's packer uses `evani/commons/out`, which Evani.App's Share reads). It never uploads.
- **A round already folded into the main branch** (2026-11-11) packs by itself: give its commit with `--commit` and no `--base`. Its merge base with the main branch is the round itself (no change on top), and the engine under it may be older than the server's render app (`ea0dd440`), the two walls folded rounds used to hit. The export finds the fold (the first main-branch first-parent commit that holds the round), takes the round's change as it was on the engine under it (the merge base with the main branch just before the fold: the patch an unfolded package would have had) and runs every rule on it as usual (allowed paths, code safety, Cargo.toml features, the server's patch rules). Then it picks the **engine commit**: the first main-branch commit from the fold on that has the render app and still holds the round's own copy of every file the round changed (the same blob for code and shaders; the asset's own library entry less its review record, `realism`, `notes`, `status`, which later folds rewrite; the Cargo features the round changed; dev-scene files are noted, the server never builds them). The patch is empty (`code.bytes` 0, `code.paths` []), `code/base/<path>` holds those files as they are at the engine commit, and `code.folded` records `round_commit`, `round_base`, `fold`, `engine` and per file its status, how it was compared, its round and engine blobs and the copy's SHA-256; `version.fold` names the fold. The first such commit is stable, so packing again later gives the same package. A round whose files were changed again on the main branch before any commit with the render app (a later round folded over it) has no such commit and is **refused** ("no main-branch commit with the server's render app still holds what was scored"): it is no longer what the main branch holds, so the latest folded round is the one to pack. The server needs nothing new: an empty patch is allowed, and its worker skips applying one (Evani.App's `platform/protocol/commons.ts` `patchProblems`, `commonsWorker.ts`); it still builds, renders and scores the engine commit itself. **import** of a folded version writes nothing: a project whose copies are the engine commit's has it already; any other copy is refused (there is no older base to merge with): update the engine to that commit.
- **--dry-run** makes the package in the temp folder, runs every check, prints its report and hash, and keeps nothing.
- **verify** checks a folder: names and sizes, the content hash, the licence, params, the patch (allowed paths, code safety, every file rebuilt to its recorded hash), a folded version's copies (each to its record, and no other `code/base` file), the pictures.
- **import** adopts a version into the project at `--root` (default: this engine): verify, then plan every file first. A file still as the version's base takes the version's file; a file already as the version is left; a file this project changed is merged 3-way with `git merge-file` (the project's copy, the base copy, the version). **Any conflict and nothing is written**: the message names the files and says to update the engine or pick a version made on yours. Writes go through temporary files and are undone if any write fails. Line ends follow the project's copy (CRLF stays CRLF). It records the version in `catalog/procedural/commons.json` (`evani-commons-adopted/1`: version id, content hash, scores, engine commit, author, area, round, files) and writes the adopted score (the server's when given, else the maker's) into `catalog/procedural/references.json` in place. With `--check` it runs the project check before and after; a check that was clean before and isn't after undoes the whole import. Package pictures are never copied into the project, so they can't reach a game's download.
- **gate** answers the share hint (below) as JSON.

Tested (`cargo test -p evani-xtask commons`, 17 tests): the round trip (export, verify, import into a CRLF copy of the base, every file equal to the round's, adopting again changes nothing, no pictures in the project), a local change elsewhere in a file merged, a conflict that changes nothing, a check that turns unclean undoing the import, a changed patch, manifest or params refused, a stray file refused, unsafe code, a new dependency, a build script and a lock file refused, the author's own score refused, the path, line and Cargo.toml rules, the gate table, the content hash definition, the pictures, the in-place score, hand-made patches. And by hand on this repo: the clouds' round 5 exported from its column commit, adopted into a fresh worktree at its base with `--check` ("evani check: clean" before and after, every file byte-equal to the round's commit).

## 4. The share hint and the server's verdict

**Hint (the tab and `cargo xtask commons gate`):** likely to pass when the version's independent score is **higher** than the server's score of the published version for that asset and style; with none published, when it reaches the floor (3.0 unless the site says otherwise). Equal or lower never replaces. The author's own score never counts. The tab says "likely to pass: 4.0 beats the published 3.5 (the server's own check decides)".

**Verdict (Evani.App's server):** static checks (the same rules as above), then a render of its own from the engine at `engine.commit` with the patch's library paths and the params, with hidden cameras and a light swap, the published version re-rendered in the same job, and its own independent reviewer scoring both blind. Accepted only above the published version (or the floor). The owner's rule on when an accepted version goes live is Evani.App's to apply.

**The render app** (`examples/proc-field/apps/commons-render`, dev only, never a game): the proof kit's plain field with the one library asset its build lists, in the engine's realism studio (the Material library's look: soft shadows, AO, image lighting, the studio sky, every recipe a library asset paints with; an object on a grey studio sweep instead of the sky, `staging` below) and the dev hooks. The server builds it from the engine at the version's commit with the patch's engine paths (it drops `examples/proc-field/**`, so a package can't move its own cameras):

```text
cd examples/proc-field/apps/commons-render
trunk build --release --no-default-features --features evani-procedural-lib/<asset key> --public-url ./ --dist <dist>
node tools/studio/asset-shoot.mjs --dist <dist> --out <folder> --shots-file <views.json> --stats <stats.json>
```

**The maker shoots the same views** (2026-11-11; Pebbles round 3 scored 76/100 on its dev scene's picture, and the server rendered the same code at 3.0): an object round's scored picture is this app's view0, shot on the maker's PC with `tools/studio/server-views.mjs` (`build`: the command above; `shoot`: the server's six object views from Evani.App's `drawPlan` at 1536x1024, plus a labelled sheet and the mesh stats; docs/ASSET_STUDIO_GUIDE.md 1.3 step 5b). `tools/studio/server-views.test.mjs` pins the plan to the server's (view0: the asset's reference camera, `camera` in `catalog/procedural/references.json`, else yaw 0, pitch 20, the framing distance, sun 135/40; the hidden views' ranges round it); a change to `drawPlan` on Evani.App's side must change both. The package format is unchanged (`render.app` stays `examples/proc-field/apps/proc-field`, as the server requires).

**Per-object studio** (2026-11-11, the owner: "exactly the scene should be exactly the same"). References differ: the cube's backdrop is a warm 171, the oak's a neutral 154, Pebbles' 134, and their key light comes from other sides. An object's entry in `catalog/procedural/references.json` (and its `realism` in library.json; tools/procedural/gen_library.py carries both) holds, beside its `camera`, an optional **`studio`**: `{"backdrop_grey": 40..230, "floor_grey": 40..230, "warmth": -40..40}` (both greys required, warmth 0 when left out), measured on its reference picture with `python tools/studio/studio-measure.py ref <picture>`. The key light's direction is the camera's `sun_yaw_deg` / `sun_pitch_deg`; two camera keys joined: `cam_aim_y` (-1 to 1) and `cam_lens_deg` (10 to 90). `cargo xtask check` refuses a studio or camera key out of range (tools/evani-guide/src/reference_cameras.rs). `server-views.mjs` puts a studio on every view as `kit.proc_field.studio_backdrop`, `studio_floor` and `studio_warmth`, and a camera's aim and lens as `cam_aim_y` and `cam_lens_deg` (only when it sets them, so an asset without them shoots exactly as before), and shoots each object at 1536 wide **in its reference's shape** (the cube's reference is 16:9: 1536x864). The server must do the same: pass these params on every view of an object job and use the reference's shape as the item's size. Every studio-object reference with a picture has its studio (18): geometry-cube-cuboid, -bevelled-box, -uv-sphere, -icosphere, -cylinder, -cone, terrain-flat-terrain, terrain-canyons, trees-oak-trees, rocks-pebbles, -medium-rocks, -jagged-rock-formations, -rounded-river-rocks, -rock-piles, water-shorelines, buildings-office-buildings, buildings-townhouses, humans-full-npc-body-variations (sky-volumetric-looking-clouds has a grey still too, but it is a sky judged on its own staged scene, not an object). Cameras are tuned for Pebbles, the cube and the oak; the other objects take the default camera with their own studio until theirs are measured.

`python tools/studio/studio-measure.py compare <reference> <view0.png> <out>` checks a render against its reference with the owner's tolerances: backdrop and floor grey ±4, cast ≤3 apart, key-side difference (the subject's left half minus its right) ±4, the subject's fill and centre ±2% of the frame (the subject is everything far from its row's backdrop, so its contact shadow counts in both). Results, 2026-11-11 (`.evani/shots/object-staging-exact/`): Pebbles and the cube within every tolerance; the oak within all but its width and horizontal centre, because its reference shows three oaks and the asset is one tree (changing the asset is outside this work).

**Seamless sweep in every build.** The floor fades into the backdrop through the look's studio haze, a shader body (`look.stylizedpbr.haze_*`): a change rebuilds the look's pipelines in the background, tens of seconds on the material recipes' shader. Shots taken before the rebuild landed had no fade at all (the cube's views, 2026-11-11: a hard floor line); the Pebbles build happened to finish in time. Now: `window.__engine.pipelinesBusy()` (dev hooks) says while shaders or pipelines are building, and `asset-shoot.mjs` waits for it before every shot (`--busy-timeout-s`, default 180); a newer slot body supersedes a rebuild of the same slot still in flight (evani-render pipelines.rs; before, an older rebuild finishing last could put the stale body back); and the haze rises evenly **down the picture** (`look.stylizedpbr.haze_curve` 1, by inverse distance), so the floor brightens smoothly from the horizon to the asset like a real sweep instead of in a band under the horizon. **The server's shooter must wait the same way** (`pipelinesBusy()` false for about 20 frames before each capture), or use this `asset-shoot.mjs`.

All the new params are off or neutral by default: with them at their defaults a render is the one it was (the fixed camera and the orbit are unchanged; `cam_free` and `cam_pitch_deg` only gained range).

**Cameras by reference kind** (catalog/procedural/ref_classes.json `viewpoints`):

- *Object* (a): the orbit, `cam_free` 1, as before.
- *Scene* (b): the player camera, `cam_free` 2: the eye `cam_eye_m` (1.7 m) above the ground at `cam_stand` (a share of the asset's horizontal bounds radius from its centre) on the side `cam_yaw_deg` faces from, looking level towards the centre's direction (at the centre itself: the same heading), pitched by `cam_pitch_deg` (**set it to 0**: its default is the orbit's 23.81), `cam_fov_deg` (60) across. "The ground" is the asset's own highest upward-facing surface under that point (a canyon's floor inside it, a plateau's top on it), else the floor at 0. Standing at 0 on a tree puts the eye on its crown: give an object a `cam_stand` over 1.

## 5. The tab: Share, Browse, Adopt

Every procedural column has an **Evani.commons** box.

- **Check Evani.app** reads the published version and the others (`evani.commons.item`); the tab also reads the published score by itself at load, at most every 10 minutes.
- **Pack round N** (the column's best independently reviewed round): the tab starts a helper of its own (its existing `agents` ability, inside an open run; no new ability) that runs `cargo xtask commons export` with the tab's own record of that round (commit found by its review time, score, reviewer, reference, pictures) and posts the folder with the tab action `commons_packaged`. The tab reads the package's `commons.json` itself and takes it only when its hash, round and independent score are the ones it recorded.
- **Share to Evani.app** (by hand; see Auto-send below for the automatic path): on only when packed and likely to pass. The owner's own click calls `evani.commons.share({ folder })`: Evani.App checks the folder and shows its **Share card**. **Only the owner's click on that card uploads.** Apart from auto-send (below, the owner's own rule, which only sends a trusted reviewer's better score of an official asset), the tab never shares from a timer, an event or an agent's action, and a helper is told never to upload, publish or share. The server's verdict comes back as the `commons` event: "Server check: accepted · server 4.0 · published 3.5", or the refusal's plain reason.
- **Versions on Evani.app**: each version's server score, the maker's own review, author, date, size and render thumbnails (data pictures only: the tab has no network), the published one marked. **Adopt** downloads it through Evani.App (`evani.commons.download`: verified, unpacked into `evani/commons/<asset>/<style>/<hash12>/`), then a helper runs `cargo xtask commons import <folder> --server-score <x> --version-id <id> --check`, commits exactly the files it wrote (when none had other uncommitted changes) and posts `commons_adopted`. The column then shows "Starting point: Evani.commons <id> (4.0 ★)" and its author's brief says to build on it.
- **Auto-send** (v1.5.12, `autosend.js`; the owner's rule, 2026-11-07, on for everyone, a switch in the gear's settings): when a round of an official-catalogue asset gets an independent score from a **trusted reviewer model** (Claude Opus 5.5+, Claude Fable 5.1+, OpenAI Sol 6.1+, OpenAI Astra; the one list `TRUSTED_REVIEWERS`, described in docs/ASSET_STUDIO_GUIDE.md 2.4) that is higher than the best version on Evani.app for that asset and look (read through the Check Evani.app path; nothing published counts as lower, the site's floor still applies), the tab runs the same Pack round flow (its packer helper, `commons_packaged`), then `evani.commons.autoShare({ folder, asset, style, column, round, score, reviewer_model, reviewer_account })`: Evani.App's share without a click or card, into the server's render, score and approval queue (the owner approves each version before it goes live). There is no other upload path. Each round is sent at most once (`CM.sent`, keyed `<asset>@<style>/c<column>r<round>`, whatever the outcome); a failed send shows its error and is never tried again by itself (Pack and Share still work by hand); an Evani.App without `autoShare` shows "not sent: needs your click" and keeps Share on. A daily-limit reply (Evani.app checks a few versions per account a day; such a reply doesn't use the round up) is tried once more a day later, three tries at most, then it stays failed. The switch is Evani.App's own (`commons.status().autoShare`, changed with `commons.autoShareSetting({ on })` from the tab's checkbox "Send better catalogue rounds automatically") together with the tab's setting: both must be on. Equal or lower scores, untrusted or unknown models, the author's own score, assets outside the official catalogue (local or on the site) and Community items are never sent, and the box says why. The packer starts only while a run is open. The box shows the outcome (the sent round, score and reviewer, or the reason) and the sent round under Versions until the site lists it. Agents read the sends with `custom_tab_read` `commons_sends`.
- **Catch-up** (`custom_tab_call` `commons_catchup { backups: [".evani/...json"], dry_run }`, once; **only `dry_run: false` sends** (v1.5.15): a missing, dropped, `true`, `"true"` or `1` value only lists and queues, records and uses up nothing; the argument key of `custom_tab_call` is `arguments`): the best trusted round per asset and look from the board, the saved boards named (plain, storage dumps, split `state.p.*` parts) and their review feeds (a feed-only round's packer takes its commit from the column's `## Fold:` line), decided and sent the same way, under the same record. It answers the list of what it sends and skips, with reasons, and opens a run for the packers when none is open (no column resumes).
- **Durable sends** (v1.5.16; the 7 catch-up sends that vanished on 2026-11-07 and Rivers stuck at "packing"): the cause was a read of the tab's record refused by Evani.App's call limit (-32005): the tab started from an empty record and its next save wrote that over the stored one, erasing the queued sends and the catch-up's "ran once" mark (and Rivers' "sent once" entry, so it was packed again and again). Now a refused read is retried and never empties the record; a save reads first and merges (this copy's own changes win, another copy's sends and the catch-up are kept, a stored send is never dropped) and writes nothing when that read fails; a reload updates the record in place. Every send keeps its round's own record (asset, look, column, round, score, reviewer, review time), so it packs and shares without its board column, and its package is kept on the send. Every waiting state says why ("queued: waiting for an open run", "packing: its packer (id) started 07:19 UTC; waiting for it to post the package"); packing fails after 45 minutes, or at once when its packer ended without posting, with the reason. Only a strictly higher trusted score sends again: a later round of the same asset and look with an equal or lower score than one on its way or sent is not sent (Rivers rounds 3 to 7 at 3.0). **Re-run after a fix**: `commons_catchup { reset_after_fix: true }` is a dry run unless `dry_run: false`; it lists each asset's best trusted round as `send`, `already received` (the tab's own sent record, or the server's own lists of your submissions and the item's versions name it), `on its way` or `skip` with the reason and the earlier state, and the real run queues only the rounds the server never received (kept in `catchup.reruns`). `commons_sends` shows each send's state, reason, package, submission and earlier tries. The item dropdown's stars: the ratings read is retried when refused (it was often refused in a burst with the feed's reads, so the dropdown said "not rated"); with no round score anywhere, the library catalogue's own score shows as "★ 4.5 catalogue (older score)", which never sends.

## 8. The Evani Library build

The library Evani.App opens from its Evani.dev tab ("Open material library") is the material viewer (`apps/material-view`) built for the web, with every asset compiled in. Commons pushes approved versions to the website; Evani.App's library builder (on the check worker's machine) turns the published set into one library build and puts it on the file host, and every Evani.App pulls it from there, without waiting for an app update. This engine's part is one command:

```text
cargo xtask library build [--out <folder>] [--modules]
cargo xtask library check <folder>
```

- **build** runs `cargo xtask build material-view --ship` (the ship build: only the modules `apps/material-view/evani.toml` lists, no live module and no dev-only code, the ship guard, `build-facts.json`, `ENGINE-LICENSE.txt`), copies it into `<folder>.building` beside `--out`, writes the version stamp `library-contents.json`, checks the folder (as **check**), and only then swaps it into `--out` (the old copy is moved aside and put back if the move fails; a failed build leaves the old library untouched). Default `--out`: `.evani/serve/material-view`, the first place Evani.App looks for a library on this PC. It prints the code download (gzip), the size of each download stage and the build's name. `--modules` adds the per-module size report (about 80 more builds, hours); without it the build is one trunk build, as the fold's rebuild of the served library is.
- **check** proves a folder's shape: `index.html`, one `*_bg.wasm` and its `.js`, `build-facts.json` (material-view, live tuning off), `ENGINE-LICENSE.txt`, the stamp naming every other file with its size and SHA-256, the ship guard on the code (no live module, no dev-only code), and Evani.App's limits (`platform/protocol/library.ts`: at most 400 files, 16 MB a file, 64 MB in all, paths of `[A-Za-z0-9._-]` parts). Every problem is listed.
- Nothing is uploaded, signed or published: Evani.App's builder hashes, gzips, signs and uploads the folder, and the owner decides releases.

The stamp, `library-contents.json` (`evani-library-contents/1`, beside `index.html`; the viewer's Library tab reads it to know which versions it carries):

| Key | What |
|---|---|
| `build` | 12 hex: the SHA-256 of the file list (`<sha256>  <path>` lines, sorted), so the same files always give the same name (the manifest's `viewer.build`) |
| `base` | the full 40-hex engine commit the checkout is on (the commit every version was imported onto) |
| `engine` | `{ name: "Evani.Dev", version }` |
| `built_at` | UTC, `2026-11-10T19:02:11Z` |
| `entry` | `index.html` |
| `included` | versions imported for this build that changed code, as `asset@style#hash12` (the refs Evani.App's library jobs use) |
| `already` | versions imported for this build whose code the base already had |
| `in_base` | versions adopted in the base commit itself (`catalog/procedural/commons.json` at HEAD). The viewer carries `included`, `already` and `in_base` |
| `files` | every other file: `{ path, size, sha256, stage }`; stage 1 opens the library (page, code, snippets, facts, licence, the stamp), 2 models (`models/`), 3 pictures (`proc-refs/`, images) |
| `total` | `{ files, size }` (the stamp included) |

The lists come from `catalog/procedural/commons.json`, which `commons import` writes; a record changed since HEAD is this build's. The builder's steps: a worktree at the base commit, `cargo xtask commons import <package> --no-check` for each approved version in publish order (a conflict is that version's `held_back`), then `cargo xtask library build --out <folder>`.

### The library window

The viewer's studio page has a third tab beside Materials and Procedural, **Library**: the approved assets evani.app serves (`apps/material-view/src/studio/lib_data.rs` reads and checks, `lib_html.rs` draws, `proc_page.rs` fetches). The window downloads nothing from the internet: Evani.App downloads, hash-checks and signature-checks the library and serves the window from its own cache on 127.0.0.1. At start and on the tab's Refresh the window fetches, from beside its `index.html`:

- `evani-library.json`: the website manifest (`evani-library/1`, `platform/protocol/library.ts`) or the part the window reads (`format`, `stage` (absent: `live`), `rev`, `published_at`, `assets`; `viewer` may be left out), plus an optional `cache` block Evani.App adds when it serves a saved copy: `{ "state": "offline" | "server-error" | ..., "saved_at": "<ISO>", "checked_at": "<ISO>" }` (`ready`, `updating` and `arriving` count as fresh). 404: "No library list yet".
- `library-contents.json` (above): which `asset@style#hash12` versions this build carries; absent, the window says it is a developer build.
- `evani-library/blobs/<sha256>`: an asset's reference picture by the hash in its `reference`; the window works out the bytes' SHA-256 and shows the picture only when it matches (404: the live view's card picture or a placeholder).

Each asset is checked by the protocol's rules (`readAsset`); one that fails is left out and listed with its reason ("its content hash didn't pass its check"); the rest still show. A list that fails as a whole (not JSON, a newer format) is never used: the window shows its own last good copy (localStorage) and says so, else a plain message. Rows show the name, style and category, the version name, "Approved version · improved by @handle · 4.0", the five category scores when present, and the state ("Update on its way", "Held back: ..."); a row whose asset (the library key, `rocks-pebbles`) this build has opens it in the live view with its own panel.

Measured on the owner's PC (engine ff843554, nothing imported, `CARGO_BUILD_JOBS=1` through run-low, cold target): 82 files, 9.93 MB on disk (stage 1 4.93 MB, models 3.62 MB, pictures 1.38 MB); code download 1.82 MB gzip (wasm 1.78 MB); 16 min from a cold target. The library has no size cap: The 10 MB download cap applies only to games (and playgrounds, which are game examples); the library, Scenes, viewers and tools have no size cap. Chris (2026-11-11): "the Library is not limited to the 10 MB that is only for games Library has no limit". The material viewer is a tool app (`kind = "tool"`), so `build --ship` and `library build` print its size (`package: X MB ...; no size cap`) and never refuse it for size; Evani.App's own library limits above (400 files, 16 MB a file, 64 MB in all) still hold.
