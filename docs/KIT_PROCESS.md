# Building a kit

How to build one genre kit on top of the Evani.Dev foundation. Follow it every time. One kit per session.

## The flow

target pack → spec → greybox pass + playtest bot → art pass → captures and video → automated checks → critic rounds (at most 3) → Chris's review → lessons.

The builder does steps 1 to 7. The orchestrator launches the critic (step 8); the builder fixes what the critic lists and runs the checks again; after a passing round the builder hands over (step 9) and stops. After Chris's review, the lessons go where step 10 says.

## Inputs

- The kit's row in `ROADMAP.md`: its ID, first look, physics and notes.
- `catalog/genres.json`: the kit's entry (cameras, systems, physics, image scene, compatible looks). Reference games describe mechanics only.
- `catalog/looks.json`, `catalog/effects.json`, `catalog/tiers.json`.
- The genre playbook `docs/playbooks/<genre>.md` if one exists (today `2d-platformer`, `kart-racer` and `match-3`): a checklist of what the genre must get right, each item with its reason. The critic scores it.
- The foundation, all in this workspace: crates `evani-core` (the `KitPlugin`, `LookPlugin` and `EngineModule` traits and `PluginContext`, in `evani_core::plugin`), `evani-render`, `evani-fx`, `evani-live`, `evani-physics` (features `simple`, `rigid`), `evani-net`, `evani-xr`; tools `tools/xtask` (`cargo xtask`) and `tools/evani-live-bridge`; apps `apps/sandbox` and `apps/bench`; the example kit `kits/evani-kit-example` and look `looks/evani-look-basic`. Read `docs/SPEC-M1.md` (design and layout) and `docs/LIVE_API.md` (live commands, param naming) first. README.md and DECISIONS.md exist; `docs/SPEC-M1.md` and `docs/LIVE_API.md` stay the reference for the foundation's design.
- Status of the foundation: `evani-core`, `evani-render`, `evani-fx`, the `evani.toml` reader and build in `tools/xtask`, `apps/bench` and the `evani-live-bridge` MCP server are built (evidence in `CORE_REQUESTS.md`). The render paths are built for 2D sprites and 3D forward; which parts of each tier's path are not built yet is in `assets/render_paths.json` (`cargo xtask render-paths <app>`), and `cargo xtask check` stops a game that targets a path that is not built. Log anything else you need in `CORE_REQUESTS.md` rather than inventing an API.

## Steps

1. **Claim it.** Set the row's status in `ROADMAP.md` to `in progress` and commit.

2. **Make the target pack** in `kits/<id>/target/`, before any code. It is what the critic and Chris judge the kit against. `cargo xtask review` checks that it is complete (item 16).
   - `reference-prompt.md`: the reference image prompt, built with the template below. Add `reference.png` (or `.jpg`, `.webp`) if an image was made from it.
   - `look-bible.md`: a hex palette (at least 5 colours, each with its role), a heading with "shape" in it (the shape language: silhouettes, bevels, proportions), the sky or backdrop, and a heading with "prop" in it listing at least 10 theme props (a table row or list item each, with where they go). Lighting direction is welcome.
   - `moments.md`: 5 to 8 signature moments, one `## <moment_id>` heading each, with what must be in frame and what makes it pass. Each id is a moment the game's `capture.frame {moment}` can set up (it becomes `[review] moments` for the showcase).
   - `hud-layout.md`: every HUD element, where it sits at 1080p and on a phone (portrait), and what it shows during a countdown or popup.
   - The genre playbook items that apply: `playbook.md`, or a heading with "playbook" in it in one of the files above. Copy the items from `docs/playbooks/<genre>.md` and say how this kit meets each; mark the ones that do not apply and why.

3. **Write the spec** in `kits/<id>/SPEC.md`:
   - Every gameplay system from the catalog, each turned into concrete mechanics and data (what is tunable, what lives in JSON).
   - The camera, chosen from the catalog cameras the look also supports.
   - Physics: exactly what the catalog says (`none`, `simple` or `rigid`). `none` means no `evani-physics` in this kit's build; `simple` and `rigid` are that crate's Cargo features (today a stub that compiles and reports in the overlay; planned, M1 in progress).
   - The look. If the row says `auto`, pick from `compatible_looks`, prefer a look that already exists in the workspace, and add at most one new look per kit.
   - The effects, chosen with the rules below, each with a one-line reason. List the start-up state per tier from the budget calculator (`evani_core::effects::plan_budget`, run by `FxModule`): tier points are in `assets/tiers/<tier>.json`, a tier's `effects_on` lists what starts on, and each effect's cost and value are in its `EffectInfo`.
   - The playtest bot (see "Kit cooperation"): how it plays to a win and how to a lose.
   - Link the target pack instead of repeating it.

4. **Greybox pass (build pass 1).** Build the whole game with plain shapes and no art: every system working, title screen to a win and a lose. It ends when the playtest bot reaches both a win and a lose (item 22) and nothing softlocks. Commit, then start the art pass. Fixing the rules on plain shapes is cheap; fixing them under finished art is not.
   - **The kit crate** `kits/evani-kit-<id>` (copy `kits/evani-kit-example`; add it to `members` and `[workspace.dependencies]` in the root `Cargo.toml`) with a struct implementing `KitPlugin`: `name()` returns the short id (`<id>`); `build(&self, kit: &mut PluginContext) -> Result<(), PluginError>` registers components (`component`), resources, events, systems (`system`), scenes (`scene`), input actions (`action`), data files (`data_file`, with `include_str!`), params and formulas (`formula`); the optional `start_scene()` names the first scene. The owner is stamped as `kit.<id>`. Gameplay is data-driven: levels, units, items and tuning in JSON. Every gameplay value worth tuning is a registered parameter (`param_f32`, `param_i32`, `param_bool`, `param_vec3` or `param_enum`, each taking a `ParamDef`), named with two or more dot-separated lowercase segments such as `kit.<id>.max_speed`. `baked_params` and `baked_formulas` load the tuned files that `bake.export` writes.
   - **The demo game** in `apps/<id>/` (copy `apps/sandbox`; add it to `members`) with an `evani.toml` that lists only what this game needs. The manifest format and `cargo xtask build` are built (see `docs/SPEC-M1.md`): the game's name, kit, look, effects and optional modules `physics`, `net`, `xr`, `live`, which xtask turns into Cargo features. The game builds an `App` (`App::new(name)`, `.with_kit(..)`, `.with_look(..)`, `.with_module(..)`, `.with_start_scene(..)`). It is a playable vertical slice: title screen; one short level, match or scenario using every system, with win and lose states; pause menu; settings for tier, effects, bindings and volume. Multiplayer genres ship offline-first with bots and local play.
   - **The bot and the dump**: the `playtest_win*` / `playtest_lose*` tests and the `review_dump` test (see "Kit cooperation").

5. **Art pass (build pass 2).** Bring the target pack to life: the look, the props from the look bible, the middle distance, the effects, the HUD from `hud-layout.md`, animation and sound. Keep the bot passing.
   - **Build or reuse the look** as the crate `looks/evani-look-<look-id>` (copy `looks/evani-look-basic`) with a struct implementing `LookPlugin`: `name()`, optional `points()` (budget points the look costs on every tier) and `styles()` (`StyleClasses::TWO_D`, `PSEUDO_3D` or `THREE_D`; default 3D), and `build(&self, look: &mut LookContext) -> Result<(), PluginError>`, which calls `palette`, `material` (a `MaterialDesc`), `shader_slot` (the WGSL body for a slot such as `tonemap`), `post_effect` (prefer an effect on or off), `post_param` (override another module's param default, such as `fx.bloom.threshold`) and `generator` (procedural texture or mesh). The owner is stamped as `look.<look-id>`. The kit must not depend on any specific look.
   - **Add missing effects** to `evani-fx` (today only `bloom` and `vignette` exist; the rest of `catalog/effects.json` is still to build). Each effect is its own Cargo feature in `crates/evani-fx/Cargo.toml` (the default is empty), a module `crates/evani-fx/src/<name>.rs` behind `#[cfg(feature = "<name>")]`, and WGSL files in `crates/evani-fx/shaders/`. It implements the `Effect` trait: `info()` returns a static `EffectInfo` (`name`, `cost` 0 to 3 budget points, `value` weight, `styles`, `vr_comfort_off`, `description`); `register()` adds the effect's own params (owner `fx.<name>`; `FxModule` registers `fx.<name>.enabled` and `fx.<name>.value_weight` itself); `passes()` and `pass_names()` describe its render-graph passes; `shaders()` lists its `EffectShader`s (the source starts with the marker `// evani.shader.<name>` and calls slots as `slot_<name>`); `write_uniforms()` fills the uniforms. Wire it into `FxModule::compiled()` and `FxModule::COMPILED`, add its name to `effects_on` in the `assets/tiers/*.json` files of the tiers that should start with it, and add a unit test (the existing tests also validate every WGSL file with naga). Take implementation guidance from `catalog/effects.json`.
   - **Tune it live.** Run the game with `evani-live`, connect through the MCP bridge (`evani-live-bridge mcp`, tools named `mcp__evani-live__<tool>`; the bridge is built, see `docs/LIVE_API.md` section 11), and tune with the commands in `docs/LIVE_API.md`: `param.set`, `slot.set`, `effect.toggle`, `tier.set`, `bench.run` on every tier (6.15), `compare.ab` for looks and effect weights (6.16), `capture.frame` (6.14) to check against the target pack, then `bake.export` (6.23; use `dry_run` first). The bake writes into the look and kit crates and `assets/tiers/`, plus a `CHANGES.md` in the look crate. Keep it.

6. **Captures and video.** Make every signature moment of `target/moments.md` reachable through `capture.frame {moment}`, set the `[review]` keys in `apps/<id>/evani.toml` (below), and run `cargo xtask review <id>`. Besides its earlier captures, the capture script's showcase phase sets the page to 1920x1080 (pixel looks: the internal resolution times k = ceil(1080 / internal height), such as 320x180 x 6), and for each tier (Low, Ultra) and each moment takes a full-page screenshot with the HUD, `shot-<moment>-<tier>.png`, with a burned-in label "Low · engine abc1234 · drift" in the bottom-right corner. It then records a run video, `video.webm` (10 s from the `[review] video` moment, else the first moment; needs ffmpeg on the PATH), with six frames from it, `video-frame-N.jpg`. Open the shots yourself: they must be real frames of the demo, not blank or broken.

7. **Automated checks.** Verify every item under "Done when". `cargo xtask review <id>` checks items 1, 3, 7 and 11 to 27 by itself and marks each PASS, FAIL, FLAG, not run or n/a on the card. Fix every FAIL that is yours to fix and run the review again. A "not run" means the input is missing (no geocheck report yet, no accepted captures yet, no bot tests): supply it where this process asks for it.
   - **Geometry integrity (geocheck)** is an automated check. For a 3D kit run `cargo xtask geocheck <app>` (`tools/evani-geocheck`; it also renders the debug views and highlight crops, and `--no-render` gives a quick scene-only pass); for a 2D kit run `tools/evani-geocheck-2d` on the kit's dump. Either way the report sits in `.vibedeck/geocheck/<app>/report.json`, with a readable `report.md` next to it. Any untagged issue blocks the hand-over: fix it, preferably with the engine's prevention helpers (snap-to-ground, `Footprints`, spline meshes, decals; `docs/GEOCHECK.md`), or tag an intentional case (a sign floating on purpose, a hidden bonus) in the level data with a reason (see "Kit cooperation"). While fixing, the live `debug.geometry` view paints the issues in the running game.

8. **Critic rounds (at most 3).** The orchestrator, not the builder, runs the independent critic:
   - `cargo xtask critic <id>` writes the critic packet `.vibedeck/review/<app>/critic/packet.md`: every capture, page screenshot, world-edge render, video frame and geometry debug view, the target pack, the genre playbook, the look README, the SPEC, the card, the quality bar (items 8 to 10), the rubric with its pass rule, the reply format and the earlier rounds' must-fix lists.
   - The orchestrator launches the `kit-critic` agent (`.claude/agents/kit-critic.md`) with fresh context on that packet. The critic did not build the kit, cannot change it, scores each rubric item (R1 to R11) 0 to 3 with evidence, lists the must-fix items and writes `critic-round-N.json` and `critic-round-N.md` next to the packet. For R9 it reviews the geocheck's debug-view captures in `.vibedeck/geocheck/<app>/views/` and the highlight crops next to them, and checks that every tag's reason holds.
   - Pass rule: every applicable item scores 2 or more, the mean of the applicable items is 2.3 or more, and there are no must-fix items. `cargo xtask review` recomputes this from the scores, and the stricter of its verdict and the critic's counts.
   - On a fail the builder fixes the must-fix list, runs `cargo xtask review <id>` again, and the orchestrator starts the next round. After a third failed round `cargo xtask critic` refuses a fourth: escalate to Chris with the three round reports instead of handing over.

9. **Hand over** (only after the critic passed).
   - In `ROADMAP.md`, set the status to `review` and fill Notes with the gzipped download size, the look used and anything unusual. Add what to try in the demo to `apps/<id>/evani.toml` as `[review] try = ["...", "..."]` (two to five short lines a player can follow; a "What to try" section in the kit README also works).
   - Run `cargo xtask review <id>` one last time. It builds the shipped game, runs the bench (or reuses results newer than the engine sources; `--rebench` forces a run), takes three captures on the bench camera path (or the `[review] moments`) and the showcase, runs the process checks (items 11 to 27 below, one headless Chrome session through `tools/live-check/capture.mjs`), and writes the review card to `.vibedeck/review/<id>/`: `card.md` (a plain summary on top, details below), `card.json`, `capture-1.png` to `capture-3.png` (or `moment-<name>.png`), the showcase `shot-<moment>-<tier>.png`, `video.webm` and its frames, the page screenshots `page-<name>.png` and the world-edge renders `geo-<name>-black.png` / `-white.png`. The card holds bench PASS/FAIL per tier with the failing check and numbers, the gzipped size and its change against the previous card, the modules and effects in `evani.toml` (and whether anything unlisted reached the download), the captures next to the reference image prompt, what to try, the hand-over line (measured published size and engine commit), the critic line (verdict, mean score, round count and must-fix list, with the score table under "Details"), a "Process checks" section and the "Done when" checklist below with the automatically checkable items already ticked, failed or marked not run.
   - The hand-over states the **measured published size** (the shipped build, gzipped, no `live` module) and the **engine commit** (the newest commit that touched `crates/` or `assets/tiers/`, apart from each crate's `Cargo.toml`), and the engine commit is the main line's. If it is not, merge the main line into the kit's branch first (`--main <ref>` names the main line; the default is `main`, else `m1-foundation`). Uncommitted engine changes fail it too.
   - Look at the three captures and the showcase yourself, and open one page screenshot to see the HUD over the canvas.
   - Commit with the message `kit: <id>` (the card and its size history in `.vibedeck/review/` are local and need not be committed).
   - Then stop and write the "Ready for review" report: paste the card's top section (everything above its "Details" line) as it is, which includes the critic report line and the number of critic rounds; add the measured published size, the engine commit, the critic's `critic-round-N.md` path and any core requests; and end with "QQ: check the done-when checklist in `.vibedeck/review/<id>/card.md`; the items marked QQ need a hand check and any FAIL goes back to the worker."

10. **Lessons loop** (after Chris's review). Every finding from Chris or the critic that would have helped earlier goes into the process, so the next kit starts from it:
    - Generic lessons (true of any kit) go into this file: a step, a Done-when item, or a new automatic check after the last item.
    - Genre lessons go into `docs/playbooks/<genre>.md` as a checklist item with its reason (create the playbook if the genre has none).
    - Look lessons go into the look crate's README (`looks/evani-look-<look-id>/README.md`).
    - Count Chris's fix rounds for the kit in the ROADMAP row's Notes ("human fix rounds: N"); the goal is 0 to 1. After `fix <id>: ...` work that Chris approves, run `cargo xtask review <id> --accept` to keep the showcase as the new visual-regression baseline.

## Kit cooperation

Some checks need the kit's help. They read these conventions; xtask never holds per-kit code.

- **Target pack**: `kits/<id>/target/` as in step 2. A game kept outside the engine folder
  (`cargo xtask review --app-dir <app folder>`) keeps it beside its kit crate, `<kit>/target/` next to
  the kit crate's folder (the same sibling layout as `kits/<id>` and `kits/evani-kit-<id>`), else in
  `kits/<id>/target/` of its own workspace; the SPEC.md sits beside `target/`. With neither, review and
  critic stop with an ERROR naming both places. Its card, captures, history and critic packet go to
  `.vibedeck/review/<id>/` of the game's workspace, and the engine's ROADMAP row is not part of its
  docs check.
- **`[review]` keys in `apps/<id>/evani.toml`**: `try` (what to try), `moments` (the scripted moments for the review captures; the showcase uses the target pack's moments first), `hud = ["#selector", ...]` (the DOM HUD elements; the entry `"canvas"` is a HUD the kit draws inside the canvas, see item 13), `world_edge = false` (no 3D ground), `video = "<moment>"` (where the run video starts; default the first moment), `internal_resolution = "320x180"` (pixel looks; else the "NNNxNNN internal" text in the catalog look's `render_rules`) and `phone_dpr = 3` (the device pixel ratio of the 844x390 and 390x844 phone shots, 1 to 4, default 1: a pixel-art game's whole-pixel scale comes from device pixels, so it is shot at a real phone's ratio).
- **Playtest bot**: tests in the kit crate's library named `playtest_win*` (the bot plays to a win) and `playtest_lose*` (the bot plays to a lose, for example by standing still until time runs out). Each drives the game's systems headless with a fixed seed and asserts it reached the state within a frame budget, so a softlock fails the test. xtask finds them by name in the kit's source and runs `cargo test -p evani-kit-<id> --lib -- playtest_ review_dump`.
- **Review dump**: a test named `review_dump` that, when `EVANI_REVIEW_DUMP` is set, writes `$EVANI_REVIEW_DUMP/review.json` from the kit's own data after a few simulated frames:
  `{"colours": {"player": {"name": "...", "hex": "#rrggbb", "marker": "what marks the player"}, "others": [{"name": "...", "hex": "#rrggbb"}]}, "objects": [{"name": "...", "gap": 0.0, "contact_shadow": true}]}`
  `gap` is the distance between the object's base and the ground under it (metres in 3D, pixels in 2D). An object that is off the ground on purpose (a hovering pickup, a cloud, a flying marker) carries `"intentional": "<reason>"`: check 19 skips its gap, still requires its contact shadow, and lists it as tagged.
- **Geocheck report**: `.vibedeck/geocheck/<app>/report.json`, written by `tools/evani-geocheck` (3D) or `tools/evani-geocheck-2d` (2D). Every issue has a `check` slug and a `tagged` field (3D: null, or the tag's reason as text; 2D: true or false). Tag an intentional case in the level data with its reason, never in the report: a `[[tag]]` in `apps/<app>/geocheck.toml` or `kits/evani-kit-<app>/geocheck.toml` (fields `check`, optional `object` glob, `at` and `radius`, and a required `reason`; `[thresholds]` overrides tolerances), or a `"geocheck"` array with the same fields in the kit's `data/*.json`. A tag without a reason is an error. Details: `docs/GEOCHECK.md`.
- **Free roam** (playgrounds, item 29): the kit reads the `PlayMode` resource and, under `PlayMode::FreeRoam`, keeps the same world with no goals, timer, lives, fail state or game over; it reports game over, timer expiry and lost lives on the `PlayOutcomes` resource in every mode; `KitPlugin::free_roam` returns true; and a test calls `evani_core::play::free_roam_test` (docs/PLAYGROUNDS.md).
- **Accepted captures**: `cargo xtask review <id> --accept` copies the current `shot-*.png` to `.vibedeck/review/<app>/accepted/`. Run it only after Chris approves a review; until then item 21 reads "not run".

## Boundaries

- Kit work happens in the kit crate, the look crate, `evani-fx` and `apps/<id>`.
- Small, additive, backward-compatible changes to `evani-core` or `evani-render` are allowed when every existing kit still builds and passes its tests. Record them in DECISIONS.md (planned, M1 in progress; create it if it is still missing).
- Anything bigger or breaking goes into `CORE_REQUESTS.md` with the reason. Set the row to `blocked` and stop.
- All characters, names, logos, music and art are original. Never use names, characters, tracks or trade dress from the reference games.

## Lessons from the Stage 4 to 6 kits

Generic lessons from building the kart racer, platformer, match-3, top-down, tactical-fps, base-building-rts, hexagon and pseudo-3D kits (sources: DECISIONS.md and the kit commits in `git log`). Genre lessons stay in `docs/playbooks/`.

- **Never end your turn while a build runs.** A long build, test or ship check goes in the background and you wait for its completion notice inside the same turn; a worker that stops with a build still running leaves a half-built tree and no result. Never poll in a sleep loop. Run cargo one job at a time at low priority with a capped job count.
- **Append hooks to existing lines to keep line numbers.** A panic location in the wasm carries a source line number, so adding or removing lines in a shared engine file (`lib.rs`, `gpu/frame.rs`, `gpu/mod.rs`, `shaders.rs`) changes the bytes of every game that does not use your feature. Edit in place, put a new hook on an existing line or at the end of the file, and keep a module declaration's line count. This is why the S5 renderer features (pseudo3d, ibl, point lights) arrive as "append-only hooks".
- **Prove "games that don't use it are unchanged" with SHA-1.** Build the ship wasm and js of an untouched game (match-3 is the usual probe) before and after, with `EVANI_GIT_COMMIT` pinned to one value on both sides (the engine bakes the commit id into the wasm, so otherwise every commit differs), and compare the hashes. Put the result in the merge or hand-over message.
- **A draw system must survive a missing `RenderWorld`.** Tests such as `free_roam_holds` run the kit headless, with no renderer and so no `RenderWorld` resource. Read it with `world.try_res_mut::<RenderWorld>()` and `return` when it is `None`; never `res_mut` (it panics). The tactical-fps and base-building-rts kits crashed their free-roam test on exactly this and were fixed in the join. Do the same for any other resource the renderer, not the kit, inserts.
- **Hand look roles over by name, not by look.** A kit never depends on or names a look. It asks for material roles, effect ids and generator names (for example a list of material names to try, first match wins, else the look's first material) and divides its palette by the chosen material's base colour so the look decides how a surface takes light while the palette stays what the player sees. Keep the roles in kit data (`data/art.json`) so a look that has none of the names still draws. Check effect ids against `catalog/` (a handover once asked for an effect id the catalog does not have; the catalog wins).
- **Draw-only memory stays out of the simulation.** Rubble, turret turn, smoothing and similar are remembered in the draw cache, never in the sim state, so determinism hashes and lockstep stay valid.
- **Look for the shared version before writing a helper.** `docs/STAGE5_DUPLICATION_AUDIT.md` lists systems that were built twice (colour conversion, param readers, easing, hashes, shake, sound synthesis, `tunables!`). Use the shared one in `evani-core` (`ParamRegistry::f32_or` and `bool_or`, `num::approach`, `num::wrap_angle`, `num::smoothstep`) and add to it rather than copying a private copy into the kit. Moving a copy over must not change behaviour: same formula, same operation order, and a test or hash that shows it.
- **Entity gather and sync is the pattern for new kits.** Rules run on plain vectors and entities are a view rebuilt each tick and written back (platformer `Objects`, match-3 `Grid`). It is deliberately not a shared helper.

## Look numbers are tunables

So a live change swaps in the part that changed instead of reloading the game (docs/LIVE_API.md 14), ask of every edit: is it a number, a colour, a shader or a layout rule? Then it is data, not code.

- **Draw dimensions and positions come from the tunable store, with defaults in code.** That includes HUD layout: banner positions and sizes, the item slot, warnings, the minimap. Register them as kit params (`kit.<kit>.hud_*`, unit `u` for HUD units) and read them each frame; never hard-code them in a draw call or a stylesheet. The kart racer's `hud_layout.rs` is the example.
- **The page reads them as CSS variables** that the app writes on its UI root only when a value changes, and the stylesheet falls back to the same defaults (`calc(var(--u) * var(--hud-wrong-top, 19))`). A test checks the fallbacks equal the code defaults.
- **HUD styles go in their own stylesheet** (`apps/<id>/hud.css`, linked with `<link data-trunk rel="inline" type="css" href="hud.css">`), so a saved style edit swaps into the running game.
- **Static page text sits in an element with an `id` and no ids inside it**; elements the code fills stay empty in `index.html`. Then text edits swap in place too; changing ids or the structure the code binds to needs a reload.

## Choosing effects

An effect earns its place only if it does one of two things:
1. **Helps the player read the game**: speed, impacts, damage, danger, where things are.
2. **Sells the look**: the look's own signature effects, such as outlines for toon or palette lock for pixel art.

Then check:
- **Pace.** Fast genres want motion feel (speed lines, trails, screen shake, hit-stop). Slow and cozy genres want atmosphere (day-night, wind sway, weather, colour grading).
- **Clarity.** Strategy and competitive genres need clarity over spectacle: avoid depth of field, motion blur, chromatic aberration and heavy grain.
- **Camera.** Top-down and isometric cameras use shadows and ambient occlusion for depth. First person uses decals and impact particles.
- **Budget.** The tier budget calculator decides what each tier keeps. VR always disables comfort-off effects.

Start from no effects and add one at a time in a live session (`effect.toggle`, then `capture.frame`). Keep an effect only if the capture is clearly better. An effect's style classes decide whether it applies to the look (`OffByStyle`), and `plan_budget` itself switches comfort-off effects off on the stereo VR tier (`OffByVrComfort`).

## Reference image prompt template

```
In-game screenshot from an original <genre name> video game, <camera framing>.
<image_scene from catalog/genres.json>
Art style: <look name>. <look description from catalog/looks.json>
<quality line: 3D looks "Top-quality real-time 3D at the engine's Ultra tier: rich global illumination, soft shadows, clean anti-aliasing, film-quality colour grading."; 2D looks "Crisp, polished 2D at native resolution: clean edges, readable silhouettes, rich colour and lighting where the style allows.">
```

## Automatic checks (items 11 to 27, and 29)

Items 11 to 27, apart from 17, and item 29 are checked automatically by `cargo xtask review <id>` (`tools/xtask/src/checks.rs` for 11 to 15, `kitchecks.rs` for 16 on, and `critic.rs`; all registered in `review.rs`) and marked on the card: PASS, FAIL, FLAG (a difference for a person to judge; it does not fail the hand-over), not run (the input is missing; listed on the card's top line, and it does not count as a pass) or n/a (the check does not apply to this kit). Items 17 and 28 are hand checks. **Later automatic checks are appended after the last item** with the next number: add a function in `checks.rs` or `kitchecks.rs` with unit tests, an `AutoCheck` variant with its wording hook in `review.rs` (the item's text must contain the hook phrase, in any case, and no other check's hook), a gather step in `cmd_review`, and the item here. Never renumber earlier items.

How they are checked, and what they miss:

- **11, tier cost order.** The same rule as the bench (`evani_bench::order_failures`): per tier the median GPU ms per frame, and each tier of Low, Medium, High, Ultra may be at most 10 % (or 0.05 ms, whichever is larger) under the one below it. The numbers come from the latest `cargo xtask bench --stress` run when it is newer than the engine sources: the stress scene (the same content for every tier, so only the tier settings differ, heavy enough to keep the GPU clocked up under Chrome's 60 Hz cap), the median of at least 600 GPU readings per tier per run, then the median of 5 runs. Without a fresh stress run it falls back to the bench path's per-tier median from the review's own bench run and says so on the card; that one can swing 2 to 5 times with the GPU's power saving at light load. A tier with no GPU time fails, because the order cannot be shown. It judges the tier settings on the stress scene, not the kit's own scenes.
- **12, architecture.** Reads `entities` from `session.status` at the boot view and after each review capture, and the registered params from `schema.get`. Fails on 0 entities in any view (a kit that keeps its game in its own structs shows none) and on no `kit.<id>.*` param. It counts entities only: it does not look for constants hard-coded in systems or for gameplay state kept outside the ECS next to some entities.
- **13, captures.** `cargo xtask review` makes the capture script hide `#evani-overlay` and `#evani-panel` with a style rule for the whole run (no engine flag), then after every review capture reads the DOM (is any of them visible?) and each `[review] hud = ["#selector", ...]` entry (matched, visible: shown, at least 4 x 4 px and on screen, not transparent, with text or an svg, img or canvas inside) and saves `page-<name>.png`. A kit that declares no HUD fails, so "no HUD" is a finding. It is DOM based: the `capture-N.png` / `moment-<name>.png` pictures come from the colour target and never contain DOM, so only the page screenshots and the showcase show the HUD; split-screen HUD parts the selector does not name are not seen. A HUD drawn inside the canvas (a pixel HUD on the art grid) is declared as `hud = ["canvas"]` and the kit sets evani-render's `RenderWorld::hud_layers` to its HUD sprite layers: the renderer then reports, with every capture, the HUD sprites of that very frame (`canvas_hud` in the `capture.frame` reply: how many with a visible tint, and their bounding box clipped to the canvas), and the entry counts as visible and filled when at least one HUD sprite is on the canvas over at least 4 x 4 CSS px. It proves the HUD was drawn in each captured frame; whether it reads well stays a hand check (item 8) on the page screenshots.
- **14, world edge (geocheck).** For each camera the same frame is rendered with `render.clear_color` black and then white (it is also the fog colour, so sky and fog follow it). Pixels that follow the clear colour are background; the camera pose from the `capture.frame` reply gives each pixel's angle below the horizon. Two rules. A soft edge: background more than a tolerance under the horizon (at least 1.5 degrees, and more for a high camera, so that the ground must reach at least 600 m before fog may hide it) over more than 0.2 % of the picture. A hard edge, at any camera height: background more than 1.5 degrees under the horizon with solid world (black and white renders within 60 % of the background difference) in the 3 rows right below it, across more than 2 % of the picture's width; this is the crisp end of a ground plane, which fog does not excuse. Either fails the camera by name. The hard-edge rule was added after the kart title screen showed the end of its ground while the check passed (the 250 m reach it used then forgave 16 degrees for that 72 m high orbit); a regression test keeps those renders failing. Limits: it assumes the ground is the plane y = 0 and world up is +Y; it only sees what the scripted cameras see (the boot view, `[review] moments` and the bench path, not a player's free camera, split-screen or a results screen unless a moment shows it); a game with no 3D ground sets `[review] world_edge = false` and the item reads "not applicable".
- **15, hand-over.** The card states the published size and the engine commit; it fails when the commit is not the main line's (`git log -1 -- crates assets/tiers`, minus each crate's `Cargo.toml`), when the engine has uncommitted changes, or when no size was measured.
- **16, target pack.** Reads `kits/<id>/target/`: `reference-prompt.md`; `look-bible.md` with at least 5 distinct `#rrggbb` colours, a "shape" heading, "sky" or "backdrop", and at least 10 rows or list items under a heading with "prop"; `moments.md` with 5 to 8 `## <id>` moments; `hud-layout.md` mentioning 1080 and phone; the playbook items (`playbook.md` or a "playbook" heading). It checks that the pieces exist, not that they are good: the critic judges that.
- **18, signature-moment captures.** For every moment of the target pack (else `[review] moments`) on Low and Ultra: the shot exists, is at least 1920x1080 (pixel looks: an integer multiple of the internal resolution, at least 1080 high), and its burned-in label names the tier and the current engine commit; and the run video lasts at least 3 seconds. It cannot tell whether the frame shows what the moment asks for: the critic does (R1).
- **19, contact shadows.** Reads `objects` from the kit's review dump: every gap at most 0.05 m (3D) or 1 px (2D) except objects tagged `intentional` (listed as tagged in the evidence), and in 3D `contact_shadow: true` for all of them. No dump means not run. It trusts the kit's own numbers; the critic and the geocheck's debug views look at the pictures.
- **20, distinct colours.** Reads `colours` from the review dump and compares them in CIE Lab (CIE76 ΔE): every pair at least 20 apart, the player at least 40 from every other colour, and the player's `marker` (an arrow, outline, label) not empty. It judges each racer's or unit's main colour, not the whole model or the lighting.
- **21, visual regression.** Compares each `shot-*.png` with its twin in `accepted/`: the share of pixels whose largest channel difference is over 32, ignoring the label. Over 10 % is a FLAG with the shot named, for the critic and Chris; a different size is a FLAG too. With nothing accepted yet it is not run. A FLAG is not a failure: art passes change pictures on purpose.
- **22, playtest bot.** Runs the kit's `playtest_win*` and `playtest_lose*` tests: at least one of each passes and none fails. Missing tests mean not run (and item 17 cannot be shown). It is only as good as the bot: a bot that cheats past a softlock hides it.
- **23, geocheck.** Reads `.vibedeck/geocheck/<app>/report.json`: any issue without a `tagged` flag or reason fails; no report means not run. xtask only reads the report; the geocheck tools make it, and the critic reviews their debug-view captures (R9).
- **24 to 26, 2D checks.** Read the same geocheck-2d report, by the issues' `check` slug: `camera` (framing zone, terrain share), `bot` (reachable collectibles, coin arcs, hidden hazards, completable level) and `popups` (the UI text rule). A kit whose catalog look has `style_class` other than "2d" reads n/a.
- **27, critic.** Reads the newest `critic-round-N.json` in `.vibedeck/review/<app>/critic/`, recomputes the verdict with the pass rule of step 8 and shows the verdict, mean score, round count and must-fix list. No round yet means not run.
- **29, free roam.** Applies to playgrounds only (a game for the Evani.app library, `[playground]` in `apps/<id>/evani.toml`; anything else reads n/a). It passes when evani.toml says `free_roam = true`, the kit's `KitPlugin` has `fn free_roam`, and the kit (or the game crate) has a `#[test]` that calls `evani_core::play::free_roam_test`; the same rule makes `cargo xtask check` print an ERROR and `cargo xtask build <id> --ship` refuse the build. The test itself runs with the kit's tests (`cargo xtask check --full`): it plays the kit in `PlayMode::FreeRoam` for the seconds it asks, with its scripted input, and fails on any game over, timer expiry or lost life the kit reports on `PlayOutcomes`, on an overlay error, or when the mode falls back to Play. It trusts the kit to report those on `PlayOutcomes` (in every mode); a kit that ends the run some other way is only caught by a person or the critic. For a playground the ship build also fails with an ERROR and a `fix:` line when the ship folder is over 10 MB uncompressed (docs/PLAYGROUNDS.md).
