# 07 Search and multi-fidelity scoring

M0 clean-room note, 2026-10-15. Own words; no third-party code opened or copied.

## What it must do (brief, design instruction 7 and tests C, D, E)
Quasi-random sampling inside the style's ranges; a cheap low-resolution pass prunes most candidates and survivors get higher-resolution scoring (successive halving); early stop when the top candidates converge; scores are silhouette IoU per view, proportions against the style, every must test (hard pass or fail) and an optional image-text score; top K returned with compact scorecards. Budgets: make within 3 s exploring at least Pro 512, Standard 256, Lite 64, CPU-only 32 candidates.

## Known approaches
- **Several attempts per part, keep the best** (ShapeCraft arXiv 2510.17603); **generate, then fix with a critic** (LL3M, CADSmith, aDSL). Few candidates, each expensive (a language-model round of minutes; aDSL reports about 190 s per round).
- **Quasi-random sequences** (Sobol, Halton, the additive-recurrence "R-d" sequence described by M. Roberts, 2018) cover a box more evenly than random points, so fewer samples find good regions.
- **Successive halving and Hyperband** (Jamieson and Talwalkar 2016; Li et al. 2017): give many candidates a small budget, keep the best fraction, give them more, repeat.
- **Image-text scoring** (SigLIP 2 arXiv 2502.14786): rank renders against words; useful for "does it look like a kart", weak for exact proportions.

## Our approach
- **Search space.** The class template plus intent fix the part graph; the search varies only the free continuous parameters (typically 15 to 60 for a kart), each bounded by its adjective range from the style profile. Numbers in the intent and analytic constraints remove dimensions before sampling.
- **Prefix-stable quasi-random sampling.** Candidates are points of a scrambled low-discrepancy sequence (our own implementation of the additive-recurrence family, scrambled by a hash of the seed), mapped through the learned prior (note 09). The sequence is prefix-stable: CPU-only's 32 candidates are the first 32 of Pro's 512, so a bigger tier explores a superset. Each candidate's constraints are solved on the CPU (note 06) before any GPU work, so every machine evaluates exactly the same field programs; only the evaluation of those fields can differ.
- **Fidelity rungs from one volume, three views at once.** For orthographic front, side and top silhouettes we do not ray-march per view: we evaluate the field on a coarse grid around the model and reduce "is any cell inside" along each axis, which yields all three axis silhouettes, the volume, the bounding box, part centroids and wall thickness in one pass. Rung 0: 32 cells along the longest side; rung 1: 64; rung 2: 128 with narrow-band refinement (only cells near the surface). Non-axis views the class needs (the kart's chase camera) are made by projecting the same grid's cells into that view instead of ray marching, so every view is a count of cells and the interval rule below covers all of them (ray marching is only used for pictures, note 21). Lengths (box, thickness) come from cell indices and volumes from integer cell counts, so tiling and summation order cannot change them.
- **The schedule is fixed before the search starts.** The search effort is a level from a fixed ladder (32, 64, 128, 256, 512, 1024 candidates), and each level has one published schedule (MODEL_API.md 1.8): how many candidates enter each rung, each rung's resolution, how many finalists, the refinement starts, population and generations (note 08) and the early-stop rule. `explore: auto` picks a level once, before the search, from the compute tier and the call's time budget (note 18); nothing during the search reads the clock (the only clock use is a safety stop past ten times the budget, which returns an error and no model; MODEL_API.md 1.8). The budget is counted in candidates, rungs and generations, never in milliseconds, so a slow machine runs the same schedule as a fast one, only for longer.
- **Successive halving with must-gates first.** At each rung: cheap must tests that are already decidable (fit box, ground contact, connectivity at that resolution) reject candidates; then the score ranks the rest; the schedule's count moves up a rung (a quarter, never fewer than 8). Level 512: 512 → 128 → 32 → 8 finalists.
- **Every keep or drop decision is the one the CPU would make (decide by interval, settle on the CPU).** The rule that makes GPU exploration safe:
  1. *The CPU is the reference.* For every rung there is one exact score: the CPU path's score (note 05: fixed operation order, no fused multiply-add, our own maths) of the same grid at the same resolution, a cell being inside when its field value is below zero. A machine without a GPU computes exactly this.
  2. *The GPU returns intervals, not numbers.* Given a per-adapter bound e on how far a GPU field value can be from the CPU's, a GPU cell is *certainly inside* below −e, *certainly outside* above +e and *uncertain* in between. Every score term is a count of cells or pixels, so the GPU returns a low and a high score per candidate: uncertain cells counted the unfavourable way, then the favourable way. While the bound holds, the CPU's exact score lies inside that interval.
  3. *Certain decisions stand; close calls go to the CPU.* To keep the best n of a rung, a candidate is certainly in if fewer than n others could beat it (their high score above its low score), and certainly out if at least n others beat it for sure (their low score above its high score). Every other candidate (its interval straddles the cut) is re-scored exactly on the CPU at that rung, and the remaining places are filled by exact score. The kept set is therefore the set the all-CPU run keeps. Must-gates work the same way: a candidate is rejected only if it fails with its uncertain cells counted in its favour; a must the GPU cannot decide is decided on the CPU.
  4. *Ties break on a stable key:* equal exact scores are ordered by the candidate's index in the sequence (lower first), never by arrival order.
  5. *The bound e is checked, not trusted.* It starts from the field program's own error estimate (operation count and magnitudes, which the interpreter knows), is raised to at least four times the largest GPU-to-CPU difference seen in the start-up calibration batch on this adapter, and is re-checked in every search: a fixed sample of sentinel cells per dispatch is also evaluated on the CPU; if any differs by more than e, e is doubled for this adapter (kept in the machine's calibration file) and that rung is run again. A wider e only sends more candidates to the CPU; it never changes the outcome. Test H records e per adapter.
  So a GPU run at a given level keeps the same survivors and finalists, and returns the same model, as a CPU-only run at that level, on every machine. The GPU only saves work.
- **Early stop, decided on CPU scores.** The top K (K = `return`) of every rung are scored exactly on the CPU. After rungs 1 and 2, if the CPU-scored top K are the same candidates as at the previous rung and the best exact score rose by less than the schedule's threshold, the remaining rungs are skipped and refinement runs the schedule's longer early-stop generation count (note 08). Both branches are part of the schedule, so stopping early is itself deterministic; the saving shows up as a faster reply, never as a clock-dependent result.
- **Score.** A weighted sum, with weights from the class template and no learned parts by default:
  - silhouette IoU per view against `match` references (each view reported separately);
  - proportions: distance of each named measure from the centre of its adjective range, in steps (note 02);
  - must tests: hard gates, never traded against other scores;
  - optional image-text score from a plug-in embedding model (off by default, guides only, never decides a must).
- **Scorecards.** Compact JSON per returned candidate: id, total score, IoU per view, must results (pass count and the failing ones with the measured number and the limit), the five measures furthest from their targets, and how it differs from the best candidate in words. Plus totals: the level and schedule version used, candidates explored per rung, candidates settled on the CPU, tier, time, GPU time.

## Why it should be better
- Hundreds of candidates in seconds replace a few language-model rounds of minutes each: the AI states intent once and the machine explores.
- One volume pass for all axis silhouettes and most measures makes the cheap rung really cheap, which is where successive halving saves most.
- Interval scores let the GPU settle the clear majority of keep or drop decisions and send only the close calls to the CPU, so the search keeps GPU speed and still returns the result of the exact CPU run (brief, hardware adaptivity 6). A fixed schedule instead of a clock means the result depends on what was asked for, not on how busy the machine was.

## Baseline and measure
- Ablations G: search off (one candidate at the range centres), multi-fidelity off (all candidates at the top rung within the same time), priors off.
- Measures per intent: candidates explored per rung, time per rung, IoU per view, must pass rate, calls and tokens (tests C, D, E). Candidates needed to reach the quality target across the benchmark order (test D), measured as the smallest ladder level whose result passes every must and reaches the gate IoU (the CPU score at 512 px against the reference mask, MODEL_API.md 1.7); the sequence is prefix-stable, so the levels share most of their work.
- Share of keep or drop decisions settled on the CPU, per rung and adapter, and its cost (it must stay small for the GPU to pay off).

## Risks
- **Axis silhouettes from a coarse grid** under-resolve thin parts at rung 0, so a good candidate could be pruned. Mitigation: thin parts get their own analytic silhouette contribution (their projected box, computed on the CPU) at low rungs.
- **High-dimensional spaces** (above about 60) make quasi-random coverage weak. Mitigation: priors and per-part sub-searches for independent parts (the graph says which parts do not interact).
- **Budget accuracy** on unknown hardware: the level is chosen before the search, so a machine slower than its tier expects overruns the time budget rather than cutting the search short. Mitigation: the calibration (note 18) places a slow machine in a lower tier; the reply says `over_budget` with the time taken; a run above ten times its budget is stopped with an error and no model (with a fix line naming a lower level), never returned as a result cut off by the clock.
- **Too many close calls** (an adapter with a large e, or candidates that are genuinely tied) make the CPU do most of the work. Mitigation: measured per adapter in M2; the CPU work is bounded by the rung sizes, so the worst case is the CPU-only run's time.
