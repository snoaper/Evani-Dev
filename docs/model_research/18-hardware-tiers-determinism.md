# 18 Hardware detection, compute tiers and determinism

M0 clean-room note, 2026-10-15. Own words; no third-party code opened or copied.

## What it must do (brief, hardware adaptivity 1 to 8, tests A, E, H)
Detect GPU adapter, vendor, memory and wgpu limits, CPU cores and memory, platform; expose them through `model.describe_system`. Compute tiers Pro (24 GB or more), Standard (mainstream discrete GPU or Apple Silicon), Lite (integrated or older GPU), CPU-only and Cloud, automatic and overridable. Fixed time, adaptive effort (default 3 s make, 1 s edit). Tile and stream to fit the adapter; degrade gracefully and say so. Portable: wgpu compute and CPU paths. Same result everywhere: the GPU explores only; the top candidates are re-scored and the final model compiled on a deterministic CPU path, so the same intent and seed give the same model hash on every machine.

## Known approaches
- **Vendor-specific stacks** (CUDA, as TRELLIS.2 needs: Linux, 24 GB of GPU memory per its README) give speed on one vendor only.
- **Portable GPU compute** through wgpu (Vulkan, Metal, DX12 natively; WebGPU in the browser).
- **Floating-point determinism** across machines: basic operations (add, subtract, multiply, divide, square root) are correctly rounded by IEEE 754 and give the same results on x86-64, ARM64 and WebAssembly when compilers do not fuse or reorder them (Rust does not do either by default); maths-library functions (sin, exp, pow) are not required to be correctly rounded and differ between platforms; GPU shader arithmetic has relaxed precision rules and differs between vendors and drivers.

## Our approach
- **Detection.** wgpu adapter info (name, vendor, device type, backend) and limits (maximum buffer and binding sizes, workgroup sizes and storage limits); CPU threads from the standard library; system memory from the operating system (read through the platform's own facilities, no new crates); platform and backend.
- **Flag: wgpu does not report GPU memory size.** The brief's Pro rule ("24 GB or more") needs it. Our approach: (1) on NVIDIA, read it from the driver's own command-line tool when present; (2) otherwise from a small table of known adapters keyed by vendor and device name, and Apple Silicon's unified memory from system memory; (3) always a 50 ms start-up calibration (a fixed field-evaluation batch) that measures throughput. The tier is set by memory where known and confirmed or lowered by measured throughput; `model.describe_system` says which evidence was used.
- **Flag: the workspace's wgpu is browser-only.** Cargo.toml pins wgpu with only the `webgpu`, `wgsl` and `std` features (DECISIONS.md: no native backend in native builds). tools/evani-model is a native tool and needs Vulkan, Metal and DX12. Turning these features on only for evani-model adds transitive crates; this needs Chris's approval (plan-decisions.md, D1).
- **Tiers.** Pro: at least 22 GiB of GPU memory as reported (binary units: the brief's "24 GB" class, since an A10G reports about 22.5 GiB usable and an RTX 4090 just under 24 GiB) and high measured throughput; Apple Silicon follows the same memory rule with the GPU's usable share of unified memory (its recommended working-set size), so a Mac reporting 22 GiB or more for the GPU is Pro and smaller ones are Standard; Standard: discrete GPUs and Apple Silicon (the dev machine's RTX 4060 Ti 8 GB is Standard); Lite: integrated or older GPUs, or a Standard GPU that measures slow; CPU-only: no usable adapter, or forced; Cloud: the same API served remotely (after M5, needs an Evani.app service). Override by flag, environment variable or the `tier` argument.
- **The tier is stable on one machine.** The tier decision (memory evidence plus the calibration) is stored in the machine's calibration file (in the user's local settings, keyed by adapter, driver version and tool version), so the same machine resolves `auto` the same way every time. It is measured again only when one of those keys changes or on request (`model_describe_system` with `"recalibrate": true`), and a new measurement moves the machine to another tier only when it misses the tier's reference speed by more than 25% (no flip-flopping on a busy PC).
- **Fixed time, adaptive effort, chosen before the call runs.** The effort is a level from a fixed ladder (32, 64, 128, 256, 512, 1024 candidates); each level has one published schedule (rung sizes and resolutions, finalists, refinement starts, population and generations, early-stop rule; MODEL_API.md 1.8). `explore: auto` resolves to a level once, before the search, as a pure function of the compute tier and the call's time budget: the largest level whose predicted time at the tier's *reference speed* (a published constant per tier, not this machine's measured speed) fits the budget. At the default budgets that gives test E's floors: Pro 512, Standard 256, Lite 64, CPU-only 32. Edits have their own ladder for the local re-search (note 10), resolved the same way. Nothing during the call reads the clock: a machine slower than its tier's reference finishes the same schedule late and says `over_budget`; above ten times the budget it stops with an error and no model. Scorecards report the level, the schedule version, candidates per rung, tier and time.
- **Memory safety.** Field evaluation and meshing run in tiles sized from the adapter's buffer limits and a memory budget (a fraction of reported or estimated memory); if a dispatch fails or memory is short, tile sizes halve and the scorecard says "degraded: smaller tiles" rather than crashing. CPU meshing streams octree tiles too.
- **Determinism, precisely.**
  1. *What decides the result.* Only the request (below) and the level's schedule. No wall-clock time, measured speed, thread count, tile size, GPU vendor or driver enters any decision (the only clock use is a safety stop past ten times the budget, which returns an error and no model; MODEL_API.md 1.8). Budgets are counted in candidates, rungs and generations.
  2. *The GPU explores, the CPU decides.* Candidates are generated and their constraints solved on the CPU, so every machine evaluates the same field programs. The GPU returns interval scores; every keep or drop decision, must-gate, early stop, refinement ranking and the final order follows the "decide by interval, settle on the CPU" rule of note 07, so it equals the decision of the CPU-only run. The GPU's error bound is checked per dispatch with sentinel cells and widened when exceeded, which can only send more work to the CPU.
  3. *The CPU path is reproducible bit for bit:* f32 with no fused multiply-add, fixed operation order, our own transcendental functions built from basic operations, fixed tiles merged in order, parallel results collected in index order (never in completion order), no iteration over randomly ordered hash maps on any decision or compile path, fixed iteration counts in solvers, deterministic sorting with index tie-breaks, scores from integer counts where possible.
  4. Output bytes are deterministic (note 17); the model hash is a hash of the output files, computed by our own implementation of SHA-256 from its published standard (FIPS 180-4).
- **The promise, worded precisely (decision D5).** *The same request at the same level gives the same model bytes on any machine.* A request is the canonical intent with its seed, the level, the tool version (which fixes the schedule table and the code), and the content hashes of the data it reads: style profile, class template, vocabulary, prior file (note 09), `like` items and reference masks. All of these are recorded in the scorecard and the recipe, so any result can be reproduced anywhere by passing its level as `explore` (slower on weaker machines). Compiling a picked candidate is identical everywhere in every case, because the recipe pins its parameter vector.
- **What `explore: auto` promises.** Test E sets different candidate counts per tier (Pro 512, CPU-only 32), while test H asks for identical model hashes everywhere; a tier that explores more can find a better candidate, so `auto` cannot give one model on Pro and CPU-only in general. Because `auto` resolves from the tier and the time budget only (never from this machine's measured speed), *two machines on the same tier with the same budget resolve to the same level and return the same model, however fast each is.* Machines on different tiers resolve to different levels and may return different models, each of which passes its musts; the reply names the level so either can be reproduced on the other. The candidate sequence is prefix-stable, so a CPU-only run at level 512 reproduces Pro's `auto` result exactly. Test H compares hashes at fixed levels (every machine runs the same levels) and at `auto` within each tier, and checks that no tier fails a must test that passes on another. (Alternative put to Chris in D5: `auto` fills the time budget on each machine; better results on fast machines, but two machines on `auto` would rarely match. Not recommended.)
- **Browser later (brief, adaptivity 8).** The CPU path is plain Rust with no platform calls, so it compiles to WebAssembly; the WGSL interpreter already targets WebGPU.

## Why it should be better
- The tool runs on every creator's machine, from CPU-only laptops to 24 GB workstations, with the same API and the same results for the same level.
- Time budgets are honoured by choosing the level up front from the tier, not by stopping on the clock, so meeting the budget never changes what the result is.

## Baseline and measure
- Test E per tier: make within budget at the tier's `auto` level (the candidate floors); edit under 1 s (Pro, Standard) or 2 s (Lite, CPU-only); kart compile under 10 s Standard, 30 s Lite, 60 s CPU-only. Over-budget runs are counted, not hidden.
- Test H: hashes compared across machines at every fixed level and at `auto` within each tier; GPU runs compared with the CPU-only run of the same level on the same machine; the GPU error bound e and the share of decisions settled on the CPU recorded per adapter; no tier fails a must test that passes on another.
- Our transcendental functions: maximum error against high-precision reference values.

## Risks
- **Throughput calibration noise** on a busy machine (the shared dev PC) can pick a lower tier; mitigation: the calibration is repeated once if it is far from the table's expectation, the result is stored and only revisited with the 25% hysteresis, and the override exists. Noise can change the tier (and so the `auto` level) only at a recalibration, never between two calls.
- **A GPU whose error exceeds its bound on cells the sentinels miss** could keep a different candidate than the CPU would. Mitigation: the bound starts at four times the worst calibration difference, sentinels widen it, and test H compares every GPU run with the CPU-only run of the same level; an adapter that ever disagrees is listed and runs its decisions on the CPU until fixed.
- **WGSL interpreter performance on integrated GPUs** is unknown until tested in the hardware matrix.
